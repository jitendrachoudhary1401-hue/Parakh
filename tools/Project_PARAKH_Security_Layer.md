## **1. Security Objectives**
Project PARAKH processes official enforcement data, evidentiary records, and citizen submissions. The security and compliance layer is engineered to guarantee:
*   **Data Confidentiality:** Protection of sensitive enforcement logs and user credentials against unauthorized access.
*   **Data Integrity:** Cryptographic assurance that evidentiary images and compliance verdicts cannot be altered or doctored.
*   **Non-Repudiation:** Proof of origin and time for every inspection record generated by field officers.
*   **Regulatory Compliance:** Alignment with Indian data protection laws, IT Act standards, and Legal Metrology guidelines.

---

## **2. Multi-Tiered Security Architecture**

### **2.1. Client & Edge Security**
*   **Secure Enclave Storage:** Local caching on the Flutter mobile app utilizes encrypted storage (SQLCipher/Encrypted SharedPreferences) to secure temporary inspection tokens and offline drafts.
*   **Certificate Pinning:** Protects mobile client-to-server communications against man-in-the-middle (MitM) attacks by hardcoding trusted SSL certificates within the app binary.
*   **Biometric & Token Authentication:** Enforcement officers must authenticate via OAuth2/OpenID Connect tokens paired with biometric verification (Fingerprint/FaceID) on the mobile device.

### **2.2. Transport & API Security**
*   **Transport Layer Security (TLS 1.3):** All data in transit between the mobile client/web dashboard and the FastAPI backend is encrypted using modern TLS cipher suites.
*   **API Gateway Rate Limiting:** Prevents denial-of-service (DoS) and brute-force attacks on sensitive endpoints (e.g., authentication, image uploads, evidence hashing).
*   **Role-Based Access Control (RBAC):** Granular permission enforcement at the API gateway layer, segregating capabilities across three primary roles:
    *   *Inspectors:* Limited to upload, scan, and local log review within assigned geographic zones.
    *   *Nodal Officers / Admins:* Access to statewide heatmaps, triage consoles, and administrative logs.
    *   *Citizens:* Restricted access to public reporting and tracking via the crowdsourcing interface.

### **2.3. Data Storage & Cryptographic Layer**
*   **Encryption at Rest:** All relational databases (PostgreSQL), unstructured logs (MongoDB), and cloud object stores (AWS S3) utilize AES-256 encryption.
*   **Database Isolation:** Sensitive PII and user authentication tables are isolated from public-facing analytical replicas.
*   **Key Management Service (KMS):** Cryptographic keys used for hashing and database encryption are managed via secure cloud hardware security modules (HSMs).

## **3. Evidentiary Security & Blockchain Integrity**
Because violation reports function as legal evidence for issuing statutory notices to non-compliant manufacturers, the evidentiary trail must be mathematically verifiable:

1.  **Payload Hashing:** Upon detecting a violation, the system bundles the evidentiary package:
    $$	ext{Payload} = \{	ext{Image S3 URL}, 	ext{GPS Coordinates}, 	ext{Timestamp}, 	ext{OCR Text Data}, 	ext{Inspector ID}\}$$
    A cryptographic hash is generated using the **SHA-256** algorithm.
2.  **Immutable Commitment:** The resulting hash is committed directly to the permissioned **Hyperledger Fabric** network hosted on AWS Managed Blockchain.
3.  **Verification Flow:** During legal proceedings, the defendant or judiciary can verify the integrity of the digital file by running a SHA-256 check against the immutable ledger receipt, guaranteeing the underlying photograph has not been modified since capture.

## **4. Audit Logging & Compliance Monitoring**
*   **Comprehensive Audit Trails:** Every administrative action, database query modification, and evidence export is logged with immutable timestamps.
*   **Automated Vulnerability Scanning:** Integrated CI/CD pipeline security gates scan container images (Docker) and third-party dependencies for known Common Vulnerabilities and Exposures (CVEs) before deployment.
